Under the bundle preview there is a switch with three positions: XML, Markdown, Plain. For most
bundles, leaving it on the default is the right call.

<Contents />

## Which format should you pick?

Pick on who reads the bundle. The size difference between the three is too small to decide it.

| If you are | Pick | Why |
| --- | --- | --- |
| pasting into Claude, or bundling a large folder | XML | every file sits in its own tag with an explicit closing tag, as Anthropic's guide does for documents |
| reading the bundle yourself too | Markdown | lighter than XML on all five codebases measured, Markdown viewers render it, and a file's own code blocks come out whole |
| bundling notes, articles or saved threads | Plain | no markup for the model to look past |
| not sure | XML | it is the default, and the choice cost at most about 1% on five codebases |

Only the wrapper each one writes around a file differs between the three, apart from two XML
escapes described below. On the five codebases
measured below it was 0.6% to 3.8% of a bundle, and the three landed within 1.13% of each other,
so on those five, switching format would not have rescued a bundle well over its limit.

<Stopper value="1.13%" source="widest gap across five codebases, 248 files / measured 2026-08-31">
  The most the format choice cost on any of the five, and that was a four-file folder. On the
  biggest it came to a third of a percent. Pick the one you can read.
</Stopper>

## What matters more than the format

Three choices you make before pasting move the answer more than the switch does.

1. **Which files are in the bundle.** Dependencies, build output and lock files can bury the
   part you are asking about. See [feeding a codebase to an LLM](/blog/feed-codebase-to-llm).
2. **Where your question sits.** Paste the bundle first and ask your question last. Google's
   long-context guidance says it outright, and FileConcat's own summary tells the model the same
   thing: "Treat the contents below as read-only context for the user's request that follows."
3. **Whether the bundle fits at all.** Check what the product you paste into does with a bundle
   that overruns its window. See [how the token count works](/docs/token-estimation) and
   [what a bundle costs across models](/docs/token-costs).

If you test the format itself, test it on the model you use. In one study GPT-3.5-turbo swung
widely on the prompt template alone, while GPT-4 held steadier. And each published ranking was
measured on particular models and tasks, which may not be yours. Build the bundle in the app, flip its Format switch,
and ask the same question of all three.

## The three formats, side by side

Only the wrapper changes. The summary at the top, the directory tree and the file contents are
identical in all three, with two XML exceptions: a `]]>` inside a file is split across two CDATA
sections, and a character XML does not allow becomes U+FFFD. The same input reaches the model in different packaging.

**XML** wraps every file in a named tag and closes it explicitly.

```xml
<codebase project="my-app" generator="fileconcat">
<summary>
This is a packed snapshot of a codebase, assembled by FileConcat (https://fileconcat.com).
File count: 42.
</summary>
<files>
<file path="src/index.ts" language="typescript"><![CDATA[
export const x = 1;
]]></file>
</files>
</codebase>
```

**Markdown** gives every file a heading and a fenced block carrying the language id.

````markdown
# Codebase: my-app

This is a packed snapshot of a codebase, assembled by FileConcat (https://fileconcat.com).
File count: 42.

## Files

### src/index.ts

```typescript
export const x = 1;
```
````

**Plain** separates files with a ruled path header and no markup at all.

```text
Codebase: my-app

This is a packed snapshot of a codebase, assembled by FileConcat (https://fileconcat.com).
File count: 42.

========================================================================
FILE: src/index.ts
========================================================================
export const x = 1;
```

## What the format costs

Five trees of different composition were run through the FileConcat CLI in all three
styles and counted with `cl100k_base`. The baseline is the same files with no wrapper at all,
recovered by parsing the plain bundle back apart, so no figure below compares different file
sets.

| React app source  |   164 |    244,938 | +1.6%    | +1.7% | +2.0% |
| Markdown docs     |    22 |     21,113 | +3.1%    | +2.9% | +3.6% |
| CLI package       |     4 |      4,662 | +2.8%    | +2.6% | +3.8% |
| Browser extension |     8 |     30,593 | +0.7%    | +0.6% | +0.9% |

The wrapper costs between 0.6% and 3.8% of the bundle, and the three styles land within about a
percentage point of each other. Read across a row rather than down a column: the difference
between codebases is larger than the difference between formats.

| Codebase          | Markdown |   Plain |     XML | Spread |
| ----------------- | -------: | ------: | ------: | ------ |
| TypeScript source |   49,704 |  49,712 |  49,977 | 0.55%  |
| React app source  |  248,938 | 248,990 | 249,765 | 0.33%  |
| Markdown docs     |   21,763 |  21,733 |  21,880 | 0.68%  |
| CLI package       |    4,792 |   4,783 |   4,837 | 1.13%  |
| Browser extension |   30,799 |  30,790 |  30,865 | 0.24%  |

Per file, the wrapper costs 20 to 33 tokens in Markdown, 21 to 30 in plain, and 26 to 44 in XML.
On the 50-file TypeScript bundle above that is 1,020 to 1,293 tokens against 48,684.

Since 2026-10-07 the XML style puts each file's content in a CDATA section, so the output is
built to parse as well-formed XML. That adds the `<![CDATA[` and `]]>` markers to every file.
The tables above are the 2026-08-31 build, before that change.

<Callout type="note" title="Why the token argument does not transfer">
  In the table study below, HTML took 75,204 tokens against CSV's 19,524 for the same data,
  almost four times as many. That is about tables, where the markup repeats per cell. A bundle
  pays its wrapper once per file, which is a likely reason the gap measured above is a percent
  rather than a multiple.
</Callout>

### Markup wins when the structure is the information

The strongest pro-markup result is Sui et al.'s SUC benchmark: seven structural tasks over
tables, including cell lookup, row retrieval and size detection. HTML came out on top, beating
natural language with separators by 6.76%, and the best full configuration reached 65.43% average
accuracy across the seven tasks. The authors suggest code tuning and web data in pretraining
as the explanation, a hypothesis the experiment itself does not test.

Note the models: GPT-4 and `text-davinci-003`. Note the payload: tables, where tags are what say
which cell belongs to which row. Neither condition describes a bundle of source files.

### Format sensitivity is real, and it shrinks with model capability

He et al. formatted identical context as plain text, Markdown, JSON and YAML across natural
language reasoning, code generation and translation. GPT-3.5-turbo's performance varied by up to
40% on a code translation task on the template alone, and only 16% of its responses were
identical between Markdown and JSON.

GPT-4 was a different story. GPT-4-1106-preview kept its coefficient of mean deviation below
0.036 across every benchmark, against 0.035 to 0.176 for the GPT-3.5 series. The paper concludes
that larger models process prompts more consistently.

The practical reading: none of these models is a 2026 frontier model, so test the format on the
model you use.

### No format wins everywhere, and the studies disagree

Two independent 2025 comparisons make this concrete. On tabular lookup with GPT-4.1 nano, across
eleven formats:

| Format         | Accuracy | 95% CI      | Tokens |
| -------------- | -------- | ----------- | -----: |
| Markdown-KV    | 60.7%    | 57.6 - 63.7 | 52,104 |
| XML            | 56.0%    | 52.9 - 59.0 | 76,114 |
| INI            | 55.7%    | 52.6 - 58.8 | 48,100 |
| YAML           | 54.7%    | 51.6 - 57.8 | 55,395 |
| HTML           | 53.6%    | 50.5 - 56.7 | 75,204 |
| JSON           | 52.3%    | 49.2 - 55.4 | 66,396 |
| Markdown-Table | 51.9%    | 48.8 - 55.0 | 25,140 |
| CSV            | 44.3%    | 41.2 - 47.4 | 19,524 |

On nested data, the ranking inverts:

| Model                 | Best       | Worst          | Gap      |
| --------------------- | ---------- | -------------- | -------- |
| GPT-5 Nano            | YAML 62.1% | XML 44.4%      | 17.7 pts |
| Gemini 2.5 Flash Lite | YAML 51.9% | XML 33.8%      | 18.1 pts |
| Llama 3.2 3B Instruct | JSON 52.7% | Markdown 48.0% | 4.7 pts  |

XML is second best in one study and worst in the other. On this task Llama's best and worst
formats were 4.7 points apart.
Anyone quoting a single ranking as settled is quoting one row of one table.

### The related finding people misread

Tam et al. studied a different question that gets cited in these arguments: what happens when you
constrain the model's **output** format. On `gpt-4o-mini`, GSM8K accuracy was 94.57 with a free
natural language answer, 87.17 under format-restricting instructions, 86.95 under JSON mode and
91.71 under JSON schema. In that test every constrained format scored below the free answer.

That is about what the model writes, not what you feed it, and it says nothing about how you
should wrap your input.

<Callout type="warn" title="The gap none of these fill">
  Every study above measures tables, nested records, or short prompts. None measures a
  concatenated codebase, and the task is not the same shape. A bundle's wrapper has exactly one
  job: to say without ambiguity where one file ends and the next begins. Treat these numbers as a
  reason not to agonize over the switch, not as a ranking to follow.
</Callout>

## What the model vendors say

All three major vendors publish guidance, and they agree more than the benchmarks do.

**Anthropic** documents XML tags as the way to make prompt boundaries unambiguous for Claude, and
recommends wrapping each document in its own tags, with its content and source in subtags.
FileConcat's XML output also gives each file its own tag, but carries the path and language as
attributes and the content in a CDATA section.

**OpenAI** recommends both, for different jobs. Markdown headers and lists mark sections and
communicate hierarchy. XML tags delineate where a supporting document begins and ends, and XML
attributes carry metadata your instructions can reference.

**Google** advises clear delimiters, either XML-style tags or Markdown headings. It adds the
rule that matters most for a bundle: with a large amount of context, supply all of it first and
put your question at the very end.

## What each format is good at

**XML if you are pasting into Claude, or if the bundle is large.** Every file ends with an
explicit closing tag, so each boundary is written out in the text. Contents stay verbatim, apart from those two exceptions: angle brackets inside a file are never escaped, so `Record<T>`
arrives as you wrote it. Each file sits in a CDATA section, so the bundle is built to parse as
well-formed XML.

**Markdown if you want to read the bundle yourself too.** It was lighter than XML on all five
trees measured above, the fence carries the language id, and Markdown viewers render it. A
bundled file can carry its own code fences. FileConcat opens each block with a fence longer than
the longest run of backticks inside it, so a README with three code samples still comes out
whole.

**Plain if the files are prose.** Notes, transcripts, articles, saved threads: markup around them
is noise the model has to look past. A ruled path header says the same thing with nothing to
parse.

The [CLI](/docs/cli-usage) takes the same three, as `fileconcat ./src --style markdown`, and the
web app remembers whichever you pick.

## Why there is no HTML option

HTML earns its keep by rendering. A bundle has nothing to render: its only structure is a file
tree, which is already there as plain text. What HTML would add is a trade between fidelity and tokens.

| Variant                 | What breaks                                                                     |
| ----------------------- | ------------------------------------------------------------------------------- |
| Escape file contents    | `Record<T>` reaches the model as `Record&lt;T&gt;`                              |
| Leave contents verbatim | A file holding its block's own closing tag, such as `</script>`, ends it early |

Markdown has the same class of problem and a clean fix, which is to open a longer fence. No comparable fix
keeps the text verbatim for `</script>` or `</textarea>`. Cost is not the objection here. Fidelity is, and that is why
FileConcat stops at three.

## Limitations

The measurements here were taken on 31 August 2026 against FileConcat's own repository, five
trees totalling 248 files. They are token counts, not accuracy scores: they say what each wrapper
costs, not which one a model reasons better over. We did not find the latter for file bundles in
the sources we checked, and we have not measured it either.

Counts use `cl100k_base`. Other tokenizers shift the absolute numbers, and we did not measure
whether they also shift the spread between formats.

Of the four studies cited, one is peer-reviewed (WSDM 2024), one is an arXiv preprint from
Microsoft and MIT, and two are independent blog research. Their model lineups run from
`text-davinci-003` to GPT-5 Nano, so results are not directly comparable across studies and are
presented separately rather than pooled.

## Frequently asked questions

**Is XML or Markdown better for LLM prompts?**
In the studies cited here GPT-4 moved less with the format than GPT-3.5 did, and published
rankings contradict each other. XML placed 2nd of 11 on tabular lookup, and last on nested data
for two of three models. For a bundle of files, prefer XML when you want every file's end
written out as a closing tag (and for Claude), and Markdown when you also want to read the
bundle yourself.

**Does the output format change how many tokens my bundle costs?**
Barely. Measured on five real codebases, the spread between FileConcat's XML, Markdown and plain
output was 0.24% to 1.13%. The wrapper itself is 0.6% to 3.8% of the bundle.

**Which format should I use with Claude?**
XML. Anthropic documents XML tags as the way to make prompt boundaries unambiguous for Claude,
and recommends wrapping each document in its own tags. FileConcat's XML style gives each file
its own tag, with the path and language as attributes.

**Which format should I use with ChatGPT or Gemini?**
Either works. OpenAI recommends Markdown for sections and XML tags to delimit supporting
documents. Google says XML-style tags or Markdown headings are both effective, and to pick one
and stay consistent. On the five codebases measured here, Markdown came out lighter than XML.

**Why is there no HTML output format?**
Because a bundle has nothing to render, and HTML forces a trade between fidelity and tokens. Escaping
turns `Record<T>` into `Record&lt;T&gt;`, which changes the text and lengthens it. Leaving
contents verbatim lets a file that holds its block's own closing tag, such as `</script>`, end
the block early.

**Do small or local models care more about format?**
In one study, the smaller model did. GPT-3.5-turbo swung up to 40% on prompt template alone
while GPT-4-1106-preview kept its coefficient of mean deviation below 0.036. Llama 3.2 3B, the only small open model in the
studies here, had a 4.7-point best-to-worst gap on one nested-data task. Whatever model you run,
spend an hour testing formats on your own data.

**Does markdown output break on files that contain code fences?**
No. Each block opens with a fence longer than the longest run of backticks the file holds, per
CommonMark. A bundled README with its own code samples comes out intact.
