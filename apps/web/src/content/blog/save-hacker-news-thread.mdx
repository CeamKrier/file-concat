Hacker News threads are dense in a specific way. The correction that matters can sit
four levels down, under a collapsed comment, in a subtree nobody scrolled to. The value is
in the whole tree, and the whole tree is what you cannot see.

If you want to ask a model what the thread concluded, you have to hand it the
thread, not the top of it.

## The page is not the discussion

Open a 600-comment thread and the page gives you the ones it decided to render. [more]
links stand in for the rest, and collapse toggles hide subtrees. Select all,
copy, paste, and you capture at most what the page had loaded and rendered.

Two things go missing at once:

- **The replies nobody expanded.** They are not in the document you copied because they
  were never in the page.
- **The nesting.** Indentation on Hacker News is drawn with spacer images and table cells,
  not with characters in the text, so a copy can lose who was replying to whom.

## Take the whole tree in one request

FileConcat Clipper is a browser side panel that reads the thread properly. On Hacker News
it goes to `hn.algolia.com/api/v1/items/<id>`, which returns the comment tree in
one request: no authentication, no paging, and nothing to expand first.

That means depth costs no extra request and no manual expanding, though a deeper thread
still makes a bigger file.

<Steps>
  <Step title="Open the panel on the thread">
    Click the toolbar icon. On a Hacker News thread the panel offers **Clip this thread**.
    Nothing needs expanding first, and there is no setting to get right.
  </Step>
  <Step title="Check it if you want to">
    **Peek** reads the Markdown back inside the panel before you send it. A wrong page or a
    read that stopped early shows up there, while it is still cheap to fix.
  </Step>
  <Step title="Send it to the bundler">
    **Send** pushes the clipping into an open [fileconcat.com](/) tab, opening one if there
    is none, where it becomes one bundle with a live token count.
  </Step>
</Steps>

<Callout type="tip" title="Where to get it">
  The extension is on the [Chrome Web
  Store](https://chromewebstore.google.com/detail/fileconcat-clipper/nhjmkijlimliapgbidajgbkangddnlhn),
  open source. There is a page about what it does at [/clipper](/clipper) and a
  reference at [/docs/clipper](/docs/clipper).
</Callout>

## Mind the size

A long thread can take a real portion of a context window for one discussion. That is the correct trade when the thread is the
subject, and the wrong one when it is background.

The bundler is where you find that out rather than guessing. It shows an estimated token
count as the bundle grows, and the cost and fit for the model you pick, so you know what
the discussion costs before you paste it. If it is too much, take the linked article instead and keep the thread for a
follow-up question.

<Callout type="warn" title="A snapshot, not a feed">
  A clipping is the thread as it stood when you took it. Later comments can make the same
  thread clipped tomorrow a different file. Re-clipping and sending again replaces the old file in
  place rather than adding a second copy.
</Callout>

## The front page, and everything around it

The front page is a listing, so the panel puts a tap target on each of its stories. Tap
the ones you care about and each thread is read on its own, which is how a morning of
open tabs becomes a set of files.

The more useful pattern is mixing sources. A Hacker News thread may be about a blog post,
a repository or a specification. The clipper can read many article pages on other sites with
a generic reader and no per-site code, so the post and the argument about it can go into the same bundle.
The repository can go in under it from the bundler itself. A send extends the bundle
rather than replacing it: a new path is added, and a path sent again replaces its earlier copy.

That is the question worth asking a model: not what this thread says, but where the thread
and the thing it is discussing disagree.

The clipping never passes through a FileConcat server. It is made in your browser, held in
your browser's own storage between the clip and the send, and handed to an open FileConcat
tab, or a new one. Once there, the site's session recording can show its file name, as the
[privacy page](/privacy) explains.
